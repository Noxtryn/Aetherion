# Architecture

## Layout versus the requested logical layout

The brief described a logical module tree and left the physical Gradle layout to what works best with
Fabric Loom. This is the mapping:

| Requested | Where it lives |
|---|---|
| `common/config` | `dev.freelocs.aetherion.common.config` (`ConfigStore`, `ConfigModel`) |
| `common/features` | `common.features` (`FeatureDefinition`, `SettingDefinition`, `FeatureRegistry`, `FeatureManager`) |
| `common/events` | `common.events` (`EventBus`, `Subscriptions`) |
| `common/data` | `common.data` (`Roadmap`) plus `data/aetherion/roadmap.json` |
| `common/services` | `common.services` (`I18n`, `Notifications`) |
| `common/ui-model` | `common.ui` (`UiState`, pure Kotlin) |
| `fabric-26.2`, `fabric-26.3` | `src/mc26.2`, `src/mc26.3` source sets, selected with `-Pmc_target` |
| `gui/engine` | `gui.engine` (`Draw`, `Icons`, `PerfStats`) |
| `gui/components` | `gui.components` |
| `gui/animations` | `gui.animations` |
| `gui/screens` | `gui.screens` |
| `gui/theme` | `gui.theme` |
| `gui/editor` | `gui.editor` |
| `integrations` | `core.AetherionModMenuIntegration` |

**Why one Loom project, not two modules.** Loom ties a project to exactly one Minecraft version.
Two sibling modules would have meant duplicating or symlinking the 95% that is identical. Instead one
project builds against a dependency matrix chosen by `-Pmc_target` (see `gradle.properties`), and the
few APIs that differ live in `src/mc26.x`. Every build compiles and tests the shared code against that
target's real Minecraft jar, so a signature change in either version fails the build instead of
shipping.

## Supporting 26.2 and 26.3

Found by diffing the public API of both Minecraft jars (`javap`) and then confirmed at runtime:

| Difference | Handling |
|---|---|
| Screen handling lives on `Minecraft.gui` (`gui.setScreen`, `gui.screen()`) in both | `platform.Platform` |
| Key codes are GLFW values in 26.2 but SDL scancodes in 26.3 (`A` = 65 vs 4) | Keys are only compared through compile-time `InputConstants.KEY_*` constants and persisted as key **names** (`key.keyboard.k`), never numbers |
| `InputConstants.isKeyDown(window, key)` in 26.2 vs `isKeyDown(key)` in 26.3 | per-target `PlatformInput` in `src/mc26.2` and `src/mc26.3` |
| Render types moved to a `renderpearl` package in 26.3 | no code change needed: Aurora only passes `RenderPipelines.GUI_TEXTURED` through |
| `KeyEvent.scancode()` became `keycode()` | not used; only `key()` and the modifier helpers |

Anything outside this list is not assumed compatible: each target is built and tested on its own.

## Rendering

Aurora draws through Minecraft's own GUI render-state API (`GuiGraphicsExtractor`), not through a
custom pipeline.

- **Rounded shapes** are nine-slice GUI sprites generated by `tools/gen_sprites.py` and tinted at draw
  time: anti-aliased filled rects, half-unit rings and soft glows. A rounded rect is one textured quad
  instead of dozens of scanline fills, and corners stay smooth at every GUI scale. The first version of
  this renderer was validated in a real client before anything was built on top of it.
- **Backdrop blur** uses the game's own menu-blur pipeline (`blurBeforeThisStratum`) and respects the
  player's *Menu Background Blur* option, so no custom shader is needed. It can be switched off under
  Performance, where the fallback is a plain dimmed scrim.
- **Shadows and glow** are the pre-blurred glow sprites, scaled for ambient blobs.
- **Icons** are 8x8 pixel glyphs authored as text and drawn as a minimal set of rectangles (no texture
  assets). Vertically repeated runs are merged, which measurably reduces draw calls.
- **Layering**: popups, modals, tooltips and toasts are drawn after `nextStratum()`, so they are never
  clipped by the page and never underneath it.

## Animation

`gui.animations`: a shared frame clock and three animator types - `Spring` (semi-implicit Euler,
1/240 s sub-steps, stable at any frame time), `Tween` (easing curves) and `StateAnim` (hover/focus
progress). All of them advance by frame time, step at most once per frame however often they are read,
keep value and velocity when retargeted (so interruption and reversal never jump), allocate nothing
while running, and snap to their target in reduced-motion mode.

## Features and configuration

- A `FeatureDefinition` carries id, category, text keys, default state, typed settings, dependencies,
  capability requirements, compatibility note, status and scope. The GUI renders whatever the registry
  contains; adding a feature needs no GUI code.
- `FeatureRegistry.validate()` rejects duplicate ids and settings, unknown dependencies, dependency
  cycles, and unimplemented features that are enabled or have a runtime. The mod refuses to start with
  an invalid registry.
- `FeatureManager` makes a feature active only if it is implemented, enabled, its dependencies are
  active and its capabilities are available. One idempotent `reconcile()` serves toggles, profile
  switches and capability changes, so a feature is never activated twice and event subscriptions made
  through `FeatureContext.subscriptions` are released on deactivation. A crashing feature is isolated
  and reported as *Failed*.
- `ConfigStore` writes `config/aetherion.json` (schema 2): global feature state (interface, theme,
  performance), favourites, and per-profile feature state and HUD layout. Values are validated against
  their schema on load, saves are debounced and atomic, a pre-v2 file is backed up, a corrupt file is
  quarantined, unknown or invalid data falls back to defaults.

## HUD

`HudManager` owns the active widgets and resolves placement from the profile's layout: a 3x3 anchor,
an offset, scale, opacity, layer and visibility. Text is rebuilt at a configurable interval, never per
frame. HUD elements are render-only; the editor screen is the only place they receive input, so they
cannot interfere with gameplay.

## Performance notes

- Measured, not estimated: the performance page shows `System.nanoTime` around each GUI frame.
- Steady-state label fitting and text wrapping are cached per string, so they do not allocate.
- Most remaining per-frame allocation is Minecraft's own render-state record for each draw call
  (about 0.7 KB each); Aurora's lever is issuing fewer calls. Numbers are in `TESTING.md`.
- No network access exists yet, so nothing can block the render thread; the roadmap requires every
  future request to be asynchronous, cached and rate limited.
